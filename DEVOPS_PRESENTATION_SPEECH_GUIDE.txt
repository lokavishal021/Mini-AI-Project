PHASE 2: THE REAL-WORLD DEVOPS CHALLENGE & HOW IT WAS SOLVED (Time: 1:00 - 2:30)
================================================================================
[ACTION ON SCREEN]:
- Open VS Code and click on: "AI CHATBOT/main1.py" (scroll to the call_gemini function).
- Also click on: "AI CHATBOT/docker-compose.yml".

[WHAT TO SAY]:
"Let me share a real engineering challenge we faced and how DevOps thinking solved it:

1. THE PROBLEM:
When we integrated modern large language models, our upstream API experienced 
spikes and started throwing HTTP 503 'Service Unavailable' errors. In a standard 
application, this would crash the service and leave users hanging. Furthermore, 
the application required Linux OCR and system speech libraries that normally break 
across different operating systems.

2. THE DEVOPS SOLUTION (High Availability & Failover):
In DevOps, we design for failure. In 'main1.py', I engineered an automated upstream 
failover system. The service dynamically routes queries to an ultra-reliable, 
low-latency model tier. If any endpoint hits high demand or latency spikes, the 
engine automatically fails over to a secondary model without dropping the user's session.

3. 12-FACTOR APP SECURITY:
Notice that our API keys are NOT hardcoded into git. Following the 12-Factor App 
DevOps standard, all secrets are isolated in '.env' files, guarded by '.gitignore', 
and injected cleanly into our Docker containers at runtime."

================================================================================
[ACTION ON SCREEN]:
- In VS Code, open: "AI CHATBOT/Dockerfile"
- Open your terminal and run: "docker-compose ps" (shows container running on port 5000).

[WHAT TO SAY]:
"Here is how we solved reproducibility through Containerization:

1. DOCKERFILE:
Looking at our Dockerfile, we use a lightweight Python 3.9 base image. We install 
system packages like tesseract-ocr and speech libraries directly inside the Linux 
container layer, followed by our requirements. This guarantees that anyone in the 
world can run OmniBot with zero manual environment configuration.

2. DOCKER COMPOSE:
In our 'docker-compose.yml', we orchestrate the app port mapping (5000:5000) and 
configure live volume mounts (.:/app). This creates a fast feedback loop for developers, 
allowing hot-reloading during local testing."

Instead of logging into the AWS Console and clicking buttons manually, I wrote

pipeline. Every time code is committed to the 'main' branch on GitHub, GitHub Actions 
automatically checks out the code, verifies the build, and packages the Docker container."

FREQUENTLY ASKED QUESTIONS (FAQ) - BE READY FOR THESE!
================================================================================
Q1: "Why did you use Docker instead of just running Python locally?"
A:  "Running Python locally introduces dependency drift—differences in OS, C-libraries 
    like Tesseract, and Python version conflicts. Docker packages the exact runtime 
    environment into an immutable image, ensuring 100% reproducibility across development, 
    staging, and cloud production."

Q2: "What is the difference between Docker Compose and Kubernetes here?"
A:  "Docker Compose is designed for local developer workflows and single-host orchestration. 
    Kubernetes is designed for enterprise production across distributed clusters, providing 
    automated rolling updates, multi-node load balancing, and auto-scaling."

Q3: "How do you handle security for API keys and secrets?"
A:  "We follow the 12-Factor App methodology. No secrets or API keys are ever committed 
    to version control. We use git-ignored .env files locally and Kubernetes Secrets or 
    environment variables in production."

Q4: "How does the bot handle high traffic or API failures?"
A:  "We built dual-layer resilience: At the application layer, an automatic model failover 
    handles upstream API spikes. At the infrastructure layer, Kubernetes Horizontal Pod 
    Autoscaling (HPA) scales pods horizontally based on CPU demand."
